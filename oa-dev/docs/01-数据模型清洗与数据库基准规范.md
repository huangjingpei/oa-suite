## 1. 数据资产清洗背景与治理准则

### 1.1 原系统数据层痛点分析
在原 `oa-suite` 的 `oa-front-service/sql/最新SQL.sql`（7.5MB 庞大转储）中，混杂了大量历史冗余：
1. **多套框架遗留残骸**：混杂了 SpringBlade 遗存表（`blade_*` 15张）、JeecgBoot 低代码表（`onl_*` 10张）、Demo 示例表（`jeecg_order_*`）以及未完成模块的死表，有效业务表被严重稀释。
2. **主键与索引混乱**：主键在 `VARCHAR(36)`（UUID字符串）与 `INT(11)`（自增整数）之间任意混用，导致 B+ 树索引碎片化严重，且在分布式或高并发场景下性能欠佳。
3. **字段缺乏统一审计规范**：各业务表创建时间、创建人、部门编码字段命名不一（如 `employee`、`proposer`、`agent` 混杂），有的表有修改时间，有的表完全缺失，缺乏标准的逻辑删除字段。
4. **流程与业务耦合松散**：原系统因依赖前端 `xmysql` 直接写库，业务单据仅用一个非规范的字符串 `bpm_status` 标识流程，状态含义缺乏服务端强类型约束。

### 1.2 现代数据治理五大准则
在本次重构中，遵循现代高可靠企业软件数据库规范进行全面治理：

```
                      ┌────────────────────────────────────────────────────────┐
                      │                现代数据模型五大治理准则                │
                      └──────────────────────────┬─────────────────────────────┘
                                                 │
            ┌───────────────────┬────────────────┴──────────────────┬───────────────────┐
            ▼                   ▼                                   ▼                   ▼
    【1. 统一领域前缀】   【2. 64位无符号主键】               【3. 标准审计闭环】 【4. 强类型流程规范】
    oa_sys_ (系统)        统一 BIGINT UNSIGNED                create_by / time    proc_inst_id (流程ID)
    oa_wf_  (流程)        全面支持雪花算法 (Snowflake)        update_by / time    proc_status  (状态码)
    oa_hr_  (人事)        消除 UUID 索引碎片                  is_deleted (软删除) 0草稿/1审批/2通过...
    oa_adm_ (行政)
    oa_collab_ (协同)
```

- **字符集与存储引擎**：统一为 MySQL 8.0+ 推荐的 `InnoDB`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
- **逻辑外键约束**：采用互联网高吞吐标准做法，不建立物理外键约束（Foreign Key），所有跨表关联建立显式 B+ 树普通索引（`KEY idx_*`），降低事务行锁争用。

## 3. 核心领域模型详细结构

### 3.1 轻量自研工作流引擎核心模型
为落实用户“先以自研轻量状态机为主，后期再考虑升级”的决策，流程引擎由 5 张表构成完整的状态机驱动闭环：

```
                    ┌─────────────────────────┐
                    │    oa_wf_definition     │ (流程定义: PROC_LEAVE, PROC_SEAL)
                    └────────────┬────────────┘
                                 │ 1:N 实例化
                                 ▼
                    ┌─────────────────────────┐
                    │     oa_wf_instance      │ (流程实例: 某员工发起的请假审批)
                    └──────┬────────────┬─────┘
                           │            │
             1:1 动态路由  │            │ 1:N 产生任务 / 沉淀历史
                           ▼            ▼
             ┌──────────────────┐  ┌───────────────────────────────────┐
             │ oa_wf_free_route │  │ oa_wf_task (当前待办任务)           │
             │ (审批人链条JSON)  │  │   status: 1待处理 -> 2已处理       │
             └──────────────────┘  └─────────────────┬─────────────────┘
                                                     │ 审批同意/驳回/加签后沉淀
                                                     ▼
                                           ┌───────────────────────────┐
                                           │    oa_wf_task_history     │
                                           │ (审批履历: 记录意见与操作)│
                                           └───────────────────────────┘
```

#### 流程状态生命周期约定 (`proc_status`)
所有业务单据表均包含 `proc_status` 字段，严格由服务端在审批动作中更新：
- `0`: **草稿待发**（单据已暂存，尚未进入审批流）
- `1`: **流转审批中**（流程实例已创建，任务已指派给第一级/当前级审批人）
- `2`: **审批通过/已办结**（所有节点审批完毕，单据正式生效，如请假扣除假期、用印盖章）
- `3`: **审批驳回**（审批人点击驳回，流程终止或退回发起人）
- `4`: **撤销作废**（发起人主动撤销或管理员作废）

- **部门体系**：`集团总部 (1001)` -> `总经办 (1002)`、`综合行政与人事部 (1003)`、`技术研发中心 (1004)`、`市场与运营部 (1005)`、`财务管理部 (1006)`。
- **预置用户**：

  - `adm_mgr` (行政专员，负责印章保管与公文发布)

### 4.2 核心业务字典体系
- `oa_leave_type`：年假 (`ANNUAL`)、事假 (`PERSONAL`)、病假 (`SICK`)、调休 (`REST`)、婚假 (`MARRIAGE`)、产假 (`MATERNITY`)、丧假 (`FUNERAL`)。
- `oa_seal_type`：企业公章 (`COMMON`)、合同专用章 (`CONTRACT`)、法定代表人名章 (`LEGAL`)、财务专用章 (`FINANCE`)、资质申报章 (`DECLARE`)。
- `oa_redhead_type`：重要决议 (`DECISION`)、行政通知 (`NOTICE`)、通报批评/表扬 (`CIRCULAR`)、业务指令 (`ORDER`)。
- `oa_clock_status`：正常打卡 (`NORMAL`)、迟到 (`LATE`)、早退 (`EARLY`)、外勤打卡 (`OUTSIDE`)。

### 4.3 预置流程模板
系统默认激活了 7 个开箱即用的自由流程定义：
- `PROC_LEAVE`（员工请假审批）
- `PROC_SEAL`（企业印章用印审批）
- `PROC_OVERTIME`（加班申请审批）
- `PROC_EGRESS`（员工外出报备）
- `PROC_REPAIR`（考勤异常补卡）
- `PROC_BORROW`（企业档案借阅）
- `PROC_REDHEAD`（红头公文发文拟签）

## 5. 开发者数据库初始化 Runbook

为便于在本地开发环境或 Docker 中快速还原数据库基准，请按以下步骤操作：

### 5.1 创建数据库
在 MySQL 8.0+ 客户端中执行：
```sql
CREATE DATABASE IF NOT EXISTS `oa_suite_dev` 
DEFAULT CHARACTER SET utf8mb4 
COLLATE utf8mb4_0900_ai_ci;

USE `oa_suite_dev`;
```

### 5.2 按顺序执行 DDL 与种子数据脚本
```bash
# 进入脚本目录
cd E:\OA\oa-suite\oa-dev\sql

# 导入表结构定义 (DDL)
mysql -u root -p oa_suite_dev < schema.sql

# 导入基准种子数据 (Seed Data)
mysql -u root -p oa_suite_dev < seed-data.sql
```

### 5.3 校验验证语句
执行以下 SQL 检查各模块初始化是否就绪：
```sql
-- 1. 验证表数量 (应为 18 张表)
SELECT count(*) AS table_count FROM information_schema.tables 
WHERE table_schema = 'oa_suite_dev' AND table_name LIKE 'oa_%';

-- 2. 验证初始用户与角色
SELECT u.username, u.real_name, d.dept_name, r.role_name 
FROM oa_sys_user u
LEFT JOIN oa_sys_dept d ON u.dept_id = d.id
LEFT JOIN oa_sys_user_role ur ON u.id = ur.user_id
LEFT JOIN oa_sys_role r ON ur.role_id = r.id;

-- 3. 验证预置流程模板
SELECT proc_key, proc_name, business_table, proc_mode FROM oa_wf_definition;
```
